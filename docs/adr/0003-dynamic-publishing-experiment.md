# 0003：方案 D 的发布时编译与请求时组装实验

2026-10-18 至 20 日，希望文章、附件和歌单更新时省去全站构建，讨论了浏览器渲染 Markdown、文件内容库以及服务端组装等路线。最终在独立 `dev` 分支实验方案 D：Publisher 从私密 Vault 增量编译 Markdown，将正文片段、附件和清单发布到私有 R2，再由 Cloudflare Worker 返回完整 HTML；主题组件及稳定配置仍随主题构建。这样将文章更新与主题构建分离，并保留公式预编译及完整页面响应。

实验刻意接受了发布器、存储和请求端三部分的运维成本。只有明确 `publish: true` 的内容进入清单；先上传版本化对象、再提交清单、最后清理旧对象。运行端每次核验当前清单，配合私有桶与 `no-store`，使残留对象不能绕过撤稿。第一版的单写入者是指定设备的运维约定，不是分布式锁。实验中的隔离 iframe 工具、动态附件与正文协议没有迁入当前静态分支。

## 路线选择与实际边界

原型同时比较 HTMLRewriter 和 Astro SSR。预先规定每轮每路线至少 200 次混合请求、至少 200 个实际 CPU 样本、总体 CPU p95 ≤ 7 ms，并检查完整 HTML、状态码及是否出现 CPU 超限错误；两者达标时优先 Astro 以复用组件。

2026-10-22 的 960 次配对请求中，原部署 CPU p95 为 HTMLRewriter 4 ms、Astro SSR 6 ms；带实例首次请求标记的混合测试为 7 ms 和 6 ms，因此选择 Astro SSR。遥测存在缺失，实例首次样本每路线只有三次，不能解释为全球冷启动保证。

整合后的三组混合请求 p95 为 **10 / 9 / 10 ms**，没有通过 7 ms 门槛。后续诊断提示 R2 数据、Astro 请求框架和布局组件的累计开销，尚未证明某个组件是唯一原因。原型选型通过不等于整合版获准稳定发布。

2026-10-23 重新澄清产品需求后，主线转向 [0004](0004-return-to-static-assets.md)。本 ADR 的替代状态表示主线开发方向改变；`dev` 实验保留并暂缓，并未因本次补录删除代码、Worker 或 R2。
