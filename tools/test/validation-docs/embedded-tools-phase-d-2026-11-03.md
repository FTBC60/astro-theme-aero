## 用户补充的 iPhone 实机反馈

2026-11-03，用户说明在刚才部署期间，通过 iPhone 上的 Chrome（用户说明为 WebKit）操作了线上 2048，得到以下结果：

| 用户操作与观察 | 记录结果 |
| --- | --- |
| 在棋盘操作区域滑动，方块按上下左右移动 | 用户实机反馈通过；该区域处理游戏手势 |
| 点击棋盘外区域，例如撤销按钮后，从 iframe 的非棋盘区域上下滑动 | 用户实机反馈通过；工具文档可以滚动 |
| 在 iframe 外上下滑动 | 用户反馈始终滚动父页面 |

来源为用户直接操作反馈，代理未直接操作该手机；iPhone 型号、iOS 和 Chrome 版本未提供。本次反馈不包含手机 JSON 文件选择/下载、所有方向按钮或独立 Safari 的完整矩阵，不将其自动补为通过。

对机制的解释应区分观察与推断：当前样本的 `#board` 有 `touch-action: none`，棋盘处理 pointer 手势，而说明等非棋盘区域保留原生滚动。按 [Pointer Events 3 的手势判定](https://www.w3.org/TR/pointerevents3/#determining-supported-direct-manipulation-behavior)和 [`none` 的定义](https://www.w3.org/TR/pointerevents3/#details-of-touch-action-values)，手势起点及其相关祖先的策略决定是否允许原生平移；键盘焦点不等同于持续接管整个 iframe。样本在 pointerup/cancel 或 lostpointercapture 后结束该次手势，规范也规定在 [pointerup/cancel 后释放捕获](https://www.w3.org/TR/pointerevents3/#implicit-release-of-pointer-capture)。

样本的撤销回调最后仍调用 `focusBoard()`，因此“点击撤销后可以滚动”不能直接证明“撤销释放了焦点”。目前确认的是用户所述操作流程下滚动正常，具体焦点/滚动锁定因果未经事件记录证实。阶段 C 探针曾命中非棋盘 MAIN 且未被 preventDefault，其失败尚不能仅凭本次反馈归结为从棋盘起手；原始失败和计数保留，结论限定为本机桌面 Chromium/CDP 模拟环境。

当前状态为：指定 NAS→Worker 发布链路通过，iPhone Chrome 的上述棋盘/滚动场景获得用户实机通过反馈，桌面 Chromium 模拟存在未解释差异。继续保留浏览器原生滚动与工具自行处理操作区手势的方案，本次没有修改工具代码、sandbox、主题焦点策略或高度，也没有重新部署。
